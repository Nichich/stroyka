# PR-стратегия

Как работаем с Pull Request'ами, чтобы в main попадал только рабочий код и при этом не тормозили друг друга.

## Когда открывать PR

- Когда фича готова или готов осмысленный кусок, который можно проверить.
- Можно открыть PR заранее как черновик (draft), если хочется ранней обратной связи. Тогда помечаем, что ещё в работе.

## Из какой ветки в какую

- Всегда из фича-ветки в main.
- Напрямую в main не пушим - только через PR. Это страховка, чтобы случайно не сломать стабильную версию.

## Как оформляем PR

В описании коротко и по делу:
- что сделано (одно-два предложения);
- зачем / какая задача закрывается;
- как проверить (что открыть, что нажать);
- если есть визуальные изменения - скриншот.

Заголовок понятный: "Каталог: фильтры и сортировка", а не "fix" или "update".

## Размер PR

- Лучше небольшие PR под одну задачу, их быстрее и проще ревьюить.
- Если фича большая (например весь каталог), бьём на части: сначала вёрстка, потом фильтры, потом подключение API.

## Ревью

- Минимум один ревьюер смотрит код перед мержем.
- Ревьюер проверяет: работает ли, не сломано ли соседнее, читается ли код, нет ли мусора (логов, закомментированного, демо-данных туда, где их быть не должно).
- Комментарии по делу, без придирок к стилю, если он не нарушает договорённости.
- Автор отвечает на комментарии и правит, либо объясняет, почему оставил как есть.

## Мерж

- Мержим только после аппрува и зелёных проверок (если настроен CI - сборка должна пройти).
- Конфликты решает автор ветки, не ревьюер.
- После мержа ветку удаляем, чтобы не плодить мусор.
- В main держим линейную и понятную историю.

## Чего не делаем

- Не мержим свой же PR без ревью (кроме совсем мелочей вроде опечатки в тексте).
- Не пушим в чужие ветки без спроса.
- Не тащим в один PR несвязанные изменения.
